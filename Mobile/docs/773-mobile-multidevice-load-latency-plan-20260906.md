# 移动端多设备压测与及时性验收计划

> 日期：2026-09-06
> 状态：首轮执行完成，持续扩展

## 测试拓扑

- M1：现有 Android 模拟器，独立账号、安装 ID、SQLite 与同步游标。
- M2、M3：新增独立 Android AVD，数据盘位于 E 盘，分别使用独立账号和设备身份。
- P1：Android 真机，用于前后台、锁屏、断网恢复和最终交互验收。
- D1：当前 Windows 桌面端，用于跨端消息、已读与 OA 状态对齐；桌面同步链路未修复前单独标记。

## 及时性口径

- 发送确认：服务端返回成功并替换本地临时消息。
- 同步落库：目标设备 SQLite 事务完成。
- UI 可见：目标会话列表或聊天页完成增量渲染。
- 已读传播：另一端未读数和已读游标持久化完成。
- 离线补偿：恢复网络或显式启动后追平游标，消息无丢失、无重复、顺序正确。

## 场景

1. 单聊并发：M1/M2/M3 轮流及并发发送，分别统计 P50/P95/P99。
2. 群聊并发：三端对同一测试群发送，验证顺序、去重、发送者渲染和头像合并。
3. 大批量补偿：目标端离线期间累计消息，恢复后验证分页追平和 ACK。
4. 已读同步：每台设备依次打开消息可见区域，验证跨端清零和首条未读位置。
5. 前后台与锁屏：区分长轮询同步、显式启动补偿和厂商推送唤醒。
6. 稳定性：持续运行期间记录崩溃、ANR、内存、CPU、重复弹窗和游标停滞。

## 约束

- 所有测试数据使用 `AI-UAT-` 前缀。
- 不把密码、Token、Cookie、设备指纹或附件地址写入日志和报告。
- 每台设备必须使用独立安装 ID、数据库和事件游标；不能用同一个克隆身份冒充多端。
- 服务器、Windows 或厂商推送未完成的能力按边界单独判定，不用客户端 UI 结果替代。

## 首轮实测结果

### 多设备资源边界

- 新增 `SecureAccess_Load_M2`、`SecureAccess_Load_M3` 两个独立 AVD，数据盘放在 E 盘；与原 M1 的 Android 身份均不同，报告不记录具体设备标识。
- M1、M2、M3 三台模拟器曾同时在线，另有一台真机连接。三台模拟器同时运行时 Windows 可用内存降到约 1.60 GB，因此后续采用“两台模拟器 + 真机常驻，第三台轮换”，避免宿主机换页和交换内存污染客户端性能结论。
- M2/M3 首次登录分别追平 1817/1437 个事件，500 条满批能够立即继续拉取；总耗时约 25.00/18.07 秒，单批 SQLite 提交最高 6.28/9.71 秒。该高值发生在三模拟器并发和低内存阶段，说明客户端落库对宿主机资源压力敏感。

### 在线单聊及时性

- `test02 -> test04` 首条消息 `AI-UAT-LATENCY-20260906-095155-M1-M3-001`：接收端同步阶段 6351 ms，其中长轮询等待 6202 ms、事务提交 46 ms、ACK 92 ms。
- UI 自动化首次观察到消息约 29.29 秒；该数据包含 `uiautomator` 每次抓树的额外耗时，只能当上界观察，不能直接作为产品 SLA 的 P95。
- 20 条突发消息 `AI-UAT-BURST-20260906-095410-M1-M3-001..020` 用 23.35 秒从真实输入框逐条发送。接收端滚动聊天记录后找到 20/20，顺序正确、重复 0。
- 同一采样窗口的同步阶段总耗时 P50 951 ms、P95 4063 ms、P99/最大 9185 ms，事务提交 P95/最大均 49 ms。这里的“同步阶段总耗时”包含长轮询等待事件的时间，不等于消息投递延迟；窗口还包含在线状态、好友/已读及另一终端发来的 1 条并发事件，因此不把 31 个事件全部冒充成 20 条消息样本。
- 为取得可用的消息及时性口径，另执行 `test02 -> test03` 10 条 `AI-UAT-AGE-20260906-101358-M1-M2-001..010`。发送端与接收端聊天记录均找到 10/10，顺序正确、重复 0；同步日志恰好出现对应的 10 个单事件批次，事件序号为 4391、4393……4409。
- 该 10 条消息的服务端事件年龄（负数时钟偏差样本按 0 计）P50 7 ms、P95/最大 37 ms；SQLite 事务提交 P50 38 ms、P95/最大 103 ms；ACK P50 100 ms、P95/最大 150 ms。
- 以“事件年龄 + 本地事务提交”估算目标端可持久化延迟，P50 50 ms、P95/最大 123 ms；计算到 ACK 完成则为 P50 148 ms、P95/最大 231 ms。长轮询请求耗时 P50 879 ms、P95 24076 ms 只表示请求在等待事件，不纳入消息及时性 SLA。

### 离线补偿与多端游标

- M3 完全停机时，M1 发送 30 条 `AI-UAT-OFFLINE-20260906-095750-M1-M3-001..030`，耗时 29.61 秒。
- 首次整机重启观察中，停机前最后可见事件序号为 4230，启动后日志从 4354 开始。由于 Android 可能在开机完成后通过后台组件提前启动应用，而当时又在手动启动前清空了日志，因此该次“游标跳跃”证据无效，不能据此判定服务端使用账号级 ACK。
- 进入消息页后会话摘要已经显示第 030 条；打开会话并滚动后找到 30/30，顺序正确、重复 0，历史消息回补通过。
- 随后执行严格 `force-stop`：停止前游标/ACK 为 4358/4358，确认进程不存在后发送 10 条 `AI-UAT-FORCESTOP-20260906-100549-M1-M3-001..010`。重新启动一次性收到 4360–4378 共 10 个事件，拉取 714 ms、提交 71 ms、ACK 399 ms、同步阶段总计 1197 ms。
- 接收端会话列表显示最新第 010 条和未读 10；打开聊天后找到 10/10，顺序正确、重复 0；最终游标/ACK 为 4380/4380，健康状态恢复为 `healthy`。该严格场景下移动端独立本地游标、事务后 ACK 和离线补偿通过。

### 稳定性与启动性能

- 两台常驻模拟器测试阶段未发现应用 FATAL 或 ANR。
- M1 应用 PSS/RSS 约 171.7/221.1 MB，M3 约 152.5/173.3 MB。
- M1 27 帧启动采样中，`totalSpan` P95 79.44 ms、最大 97.23 ms，11/27 帧超过 16.67 ms；首帧约 78.07 ms。启动与首屏仍需继续优化，不能以“未崩溃”代替流畅度通过。

### 登录边界

- M2 新安装后 `test03` 首次登录成功。退出后用 UI 自动化反复修改“已保存密码”输入框时，`test03/test05/test06` 曾收到统一的“账号或密码错误”；该过程会干扰保存凭据占位状态，不能作为真实用户重新登录失败的证据。
- 随后执行一次脱敏直连登录，只记录 HTTP 状态和字段存在性：返回 200，并包含访问令牌、刷新令牌、服务端设备 ID、IM/OA 地址；没有记录任何令牌、密码、指纹或响应正文。
- M2 冷启动后页面显示 `test03 / 已保存密码`，不再改写输入框，直接点击登录成功；心跳 204，IM/OA 游标健康。因此“退出后重新登录”最终通过，先前失败归类为测试自动化干扰，不列产品缺陷。

## 判定

- 在线 20 条真实 UI 发送、接收、顺序和去重：通过。
- 在线 10 条消息事件年龄与本地持久化及时性：通过；P95 123 ms，且双方记录 10/10、重复 0。
- 离线 30 条历史回补：通过。
- 移动端独立事件游标/ACK：严格 `force-stop` 场景通过；仍需用同账号两台移动安装同时在线完成最终服务端隔离矩阵。
- 三模拟器长期常驻：受宿主机内存限制，不建议；轮换方案可执行。
- 退出后重新登录：冷启动保存凭据路径通过；手工改写保存密码框的自动化脚本不纳入产品结论。

## 三 AVD 同群并发追加

三台 AVD 后续在同一测试群各发送 15 条，共 45 条；三端最终均为 45/45、发送者分布 15/15/15、序号 1..45 严格递增、消息 ID 和发送者 + `clientMessageId` 均无重复、Outbox=0、SQLite 完整性正常、事件游标 `applied=acked`。

随后严格强停 M3，M1/M2 各新增 10 条。M3 停止期间仍为 45 条；只启动一次后约 4.8 秒追到 65/65，未读正确保留为 20。该场景的数据可靠性通过。

三模拟器同时运行时最慢同步批次约 5–12 秒，M2 的 UI 输入、SQLite 提交和 ACK 均明显偏慢；宿主机三套 QEMU 工作集合计约 10 GiB，因此本结果用于暴露压力退化，不替代真机 SLA。完整记录见 [775 · 三 AVD 同群并发与离线追赶实测](775-mobile-three-avd-concurrent-group-load-20260906.md)。
