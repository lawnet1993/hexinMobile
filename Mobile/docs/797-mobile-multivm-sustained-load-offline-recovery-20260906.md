# 移动端四 AVD 持续并发、及时性与离线追平复验（2026-09-06）

## 结论

本轮在四台独立 Android AVD 上继续提高真实 UI 消息量：三台群聊端并发发送 60 条，随后停止其中一台，再由另外两台发送 20 条。最终三端均完整收敛到 324 条消息，序号、服务端消息 ID、`clientMessageId` 去重键、Outbox、事件游标和 SQLite 完整性通过。

在线阶段可用时钟样本的事件年龄最大约 4.940 秒；离线端冷启动后约 5.427 秒追平 20 条。本轮没有再次出现 20 秒级在线长尾，但样本仍不足以解除 [792](792-mobile-four-avd-im-latency-read-semantics-20260906.md) 中已复现的 20.259 秒长尾和服务端错误已读语义阻塞，因此总体仍判定为**部分通过**。

## 离线补偿与冷启动追平

1. M3 在累计 304 条、Outbox 为 0、`applied=acked=5387` 时被停止，确认进程不存在。
2. M1、M2 保持在线并分别发送 10 条，共新增 20 条。
3. M3 停止状态的只读快照仍为 304 条，证明离线期间没有伪造本地投影。
4. 冷启动 M3，不重放发送操作；轮询一致性快照观察恢复过程。

| 冷启动后时间 | M3 消息数 | 游标 |
| ---: | ---: | --- |
| 1.577 s | 304 | 5387 / 5387 |
| 2.741 s | 304 | 5387 / 5387 |
| 4.351 s | 304 | 5387 / 5387 |
| 5.427 s | 324 | 5428 / 5428 |

最终 M1、M2、M3 均为 324 条，发送者计数为 123 / 91 / 110，序号 1..324 严格递增，324 个服务端消息 ID 与 324 个发送者 + `clientMessageId` 键均唯一，Outbox 为 0，SQLite `quick_check=ok`。

离线补偿批次的最老事件年龄约 61.175 秒、最新事件年龄约 28.973 秒，这是 App 停止和发送完成到重新启动之间的预期积压年龄；它不是在线实时唤醒延迟。启动后完成本地追平的实测时间为 5.427 秒。

## 尚未通过

1. 先前纯接收端已出现 20.259 秒在线长尾，本轮 80 条增量没有再次触发，不代表问题已修复；需要服务端/Gateway 的等待器、消息提交和唤醒指标共同定位。
2. 服务端仍可能在接收端未打开会话时推进本人已读游标；服务端修复前，跨端未读/已读矩阵保持未通过。
3. 本轮没有使用厂商真机后台冻结、Doze 和系统推送通道；真机仍需解锁并开启通知权限后补测。
4. 四 AVD 是端到端正确性与客户端资源复验，不是服务端容量压测。若要测饱和点，需要单独的账号池、限流豁免和服务端监控窗口。
