# 778 · 多设备可见区域已读与跨端同步复验

> 日期：2026-09-06  
> 结论：三端压力测试遗留的 20 条未读已完成真实可见区域已读闭环；移动端没有在进入会话时一次性误清全部未读，另一台移动端也收到了部分已读和完全已读两条事件。

## 样本与基线

- 沿用 `AI-UAT-MULTIVM-20260906-1100` 三端群聊，不创建新业务数据。
- 接收端本地 65 条消息，序号 1..65 严格递增，`lastReadSequence=45`、未读 20。
- 对照端同样为 65 条消息，`lastReadSequence=65`、未读 0。
- 两端均为消息 ID 65 个唯一、Outbox 0、SQLite `quick_check=ok`、事件游标 `applied=acked`。

## 真实交互结果

1. 在接收端会话列表可见红色未读角标 20，点击进入群聊。
2. 页面定位到首条未读附近，当前可见区域最高只到序号 54；约 1.3 秒观测上界内，本地投影变为 `lastReadSequence=54`、未读 11。
3. 这说明单纯打开会话不会把屏幕外的 55..65 提前标成已读，符合“消息真正进入可见区域才提交”的约束。
4. 点击“回到最新”，约 1.3 秒观测上界内投影推进为 `lastReadSequence=65`、未读 0。
5. 对照端恢复到前台后约 6.0 秒观测上界内追平事件游标；事件收件箱新增两条不同序号的 `conversation.read`，分别对应部分已读和完全已读。
6. 追平后两端仍保持 65 条消息、65 个唯一消息 ID、Outbox 0、SQLite 完整性正常，没有因为已读事件重复插入消息。

上述时延包含 ADB、数据库一致性快照和脚本进程启动开销，只能作为端到端观测上界，不等同于网络纯投递延迟。

## 判定

- 可见区域已读：**通过**。
- 未读数量与 `lastReadSequence` 持久化：**通过**。
- 同一账号以外的跨设备 `conversation.read` 接收：**通过**。
- 重复消息与 Outbox 健康：**通过**。
- Windows 桌面端消费同一已读事件：**本轮未判定**；当前会话没有可调用的桌面窗口控制入口，不能用移动端结果替代桌面实测。
