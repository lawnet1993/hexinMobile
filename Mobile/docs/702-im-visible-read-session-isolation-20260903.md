## P1 风险：旧会话的已读链路会转用新登录身份

原 `markRead` 先读取登录A，随后每个“@我”接口重新获取当前登录。若A的 `/conversations/{id}/read` 尚在等待时已切到B，响应回来后仍写A的本地已读，再使用B调用 `/mentions/unread` 和 `/mentions/read`。同账号重新登录也有旧操作继续借用新令牌的问题。

可复现的本地测试使用回环HTTP服务器、真实本地SQLite和SecureSessionStore，不连接测试服务器：

1. 为两个隔离账号分区准备9条消息、已读0、未读9。
2. A发起可见序号7的已读请求。
3. HTTP处理器在指定阶段保存B登录（另覆盖同账号新会话）。
4. 放行旧响应，检查整个请求链的账号、会话、后续请求和两分区已读。

[直接串账号红测](../test/evidence/im-batch-catchup-20260903/read-session-cross-account-before.log) 的预期账号集合为 `[a]`，实际为 `[a,b]`。完整16项中 [修复前4过/12失败](../test/evidence/im-batch-catchup-20260903/read-session-before.log)。这证明客户端会跨登录继续调用，并不证明线上服务端实际越权成功；后端授权仍可能拦截。

## 实际改动

[协作仓库](../lib/features/collaboration/data/collaboration_repositories.dart) 的可见已读、查询未读提及、确认提及三阶段始终传递原 `MobileSession`：

- 每个请求使用原会话创建客户端，发送前、成功后、失败后均核对完整登录身份。
- 本地已读提交放入短会话锁，登录变更后不再写旧结果；锁不覆盖网络等待，不阻塞重新登录。
- 若旧请求已在原账号发出，不能撤销服务端可能已接受的操作；修复保证不再借用新账号发后续请求，也不让迟到错误影响新会话。
- 已读主请求失败仍不提交本地状态；同一会话内可选“@我”接口失败，继续保留已确认的会话已读，沿用原恢复机制。
- 不改已读序号的可见性判定、消息/群聊类型、接口正文、设备标识或账号数据隔离命名空间。

[16项新增测试](../test/im_read_session_isolation_test.dart) 覆盖三网络阶段 × 两种切换 × 200/500（12项），以及正常可见提及过滤、主请求失败、两类可选提及失败（4项）。正常路径只确认序号7及之前的提及，序号9仍未读，另一个账号完全不变。
