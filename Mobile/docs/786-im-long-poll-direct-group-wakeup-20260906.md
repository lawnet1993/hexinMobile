# 786 · IM 长轮询单聊与群聊唤醒对照实测

> 日期：2026-09-06，Asia/Shanghai。结论：客户端落库与渲染不是当前实时长尾的主因。单聊事件能及时唤醒长轮询；同一台接收端、同一套同步代码接收群聊时连续出现 7.98–14.06 秒事件年龄，服务端/网关的群成员长轮询唤醒暂判未通过。

## 测试拓扑

- Android test02：发送端。
- Android test03：接收端，保持前台在线但不打开被测群聊。
- Android test04：第三在线端，用于此前三端并发和最终一致性核对。
- Windows 已安装 test01 会话：仅通过授权测试会话执行只读长轮询探针，不以当前本机旧版 UI 代替最新版桌面验收。
- 所有新增消息均使用 `AI-UAT-` 前缀；未输出令牌、Cookie、密码、设备标识或附件地址。

## 单聊对照

test03 从移动端向 test01 发送单聊后，Windows 长轮询连续三次均收到对应 `message.created`：

| 样本 | 长轮询请求耗时 | 点击发送至返回 | 对应事件 |
| --- | ---: | ---: | ---: |
| 1343 | 612.69 ms | 591.12 ms | 1/1 |
| 1344 | 529.09 ms | 524.51 ms | 1/1 |
| 1345 | 555.46 ms | 527.95 ms | 1/1 |

移动端到移动端的单聊对照也通过：test02 向 test03 发送后，接收端请求 1,427 ms 返回，总处理 1,590 ms，本地提交 34 ms。`oldestEventAgeMs=-208` 是两端时钟约 0.2 秒偏差，不代表未来事件。

## 群聊复现

test02 向三人测试群发送，test03 的 25 秒长轮询没有在群事件创建后立即唤醒：

| 样本 | 发送前轮询边界 | 事件返回时刻 | 请求耗时 | 返回时事件年龄 | 本地提交 |
| --- | --- | --- | ---: | ---: | ---: |
| 1347 | 非边界控制样本 | 13:41:15.688 | 25,179 ms | 7,977 ms | 21 ms |
| 1349 | 13:41:58.452 | 13:42:19.818 | 21,049 ms | 14,061 ms | 21 ms |
| 1351 | 13:42:44.991 | 13:43:04.860 | 19,526 ms | 12,573 ms | 32 ms |

1349、1351 均在一个空长轮询刚完成后约 1 秒触发发送，排除了“发送发生在轮询空档”的主要可能。事件最终完整落库、ACK 成功且无重复，但实时 SLA 不通过。

## 定位结论

- 同一移动接收端的单聊可以唤醒，说明应用前台、网络、游标、SQLite 和通用拉取循环能够工作。
- 群聊事件返回后，bootstrap 8–9 ms、SQLite 提交 21–32 ms、ACK 108–114 ms；十余秒主要耗在事件已经创建但长轮询尚未返回的阶段。
- 因此不应通过压缩消息气泡、减少列表 rebuild 或改 SQLite 来修复这次长尾。
- 也不建议把 25 秒改成高频短轮询作为最终修复；这只会提高耗电和请求量，并掩盖群事件唤醒缺陷。
- 桌面 test01 的空长轮询还出现 4.52–6.36 秒提前空返回，与请求的 25 秒不一致，建议一并核对代理超时和应用层等待实现。

## 给服务端 AI 的可执行提示词

请检查测试服 `GET /api/im/sync/events?afterSequence={cursor}&waitSeconds=25&take=500` 的长轮询唤醒实现。真实证据显示：单聊 `message.created` 可在约 0.5–2.0 秒内唤醒目标账号；群聊 `message.created` 在同一 Android 接收端连续三次未即时唤醒，事件创建后约 7.98、14.06、12.57 秒才随既有轮询返回，而客户端落库仅 21–32 ms。重点检查：

1. 群消息事务提交后，是否向所有有效群成员（不能只通知发送者或当前节点缓存中的成员）发布游标推进/等待器唤醒信号。
2. 多实例部署时，等待器是否只保存在进程内；若是，使用 Redis Pub/Sub、消息总线或等效跨实例通知，按账号/设备唤醒。
3. 唤醒顺序必须是事件与收件人投递记录提交成功后再广播，接收端醒来后立刻能以原游标读到事件。
4. 检查大群成员展开、在线设备索引和账号到设备映射，不能因为会话未打开、设备为 mobile 或消息来自同账号其他端而跳过通知。
5. 核对反向代理、Gateway 与应用层 wait timeout；当前还观察到 `waitSeconds=25` 的空请求在约 4.52–6.36 秒提前返回。
6. 增加集成测试：至少 3 个账号、2 个服务实例，覆盖单聊、群聊、`@我`、未打开会话、两设备同账号、轮询建立前后竞态；断言事件无丢失/重复/乱序，并记录“事件提交至目标长轮询返回”的 P50/P95/P99。

修复验收标准：前台网络正常时，单聊和群聊目标设备的事件提交至长轮询返回 P95 不高于 2 秒；连续 100 条和 2,000 人群压力样本无丢失、重复、乱序，游标 applied=acked，离线恢复仍保持最终一致性。
