# 移动端图片压缩强杀残留与启动性能修复

> 日期：2026-09-09  
> 设备：Android 模拟器 `emulator-5556`

## 发现

图片压缩正常结束、失败或页面退回时，`finally` 会删除应用私有 `mobile-image-source-*` 临时目录；但操作系统直接终止进程时 Dart 清理逻辑不会执行，旧实现没有在下次启动删除这类大图原始缓存。

## 修复

- 增加启动清理，仅删除系统临时目录下名称以 `mobile-image-source-` 开头的目录。
- 不删除普通文件，即使文件名使用相同前缀。
- 不删除其他功能的缓存目录。
- 缓存目录不可访问、已被并发删除或单项删除失败时，不阻断应用启动。
- 清理在 `runApp` 返回后异步执行，不阻塞首帧。
- 仅清理应用启动前至少一分钟已存在的遗留目录，避免触碰当前启动期间刚创建的压缩任务。
- 压缩任务会登记活跃工作目录；启动清理在读取属性前和删除前均复核活跃集合，避免与正在执行的压缩并发冲突。

## 运行时验证

第一次实现错误地在 `runApp` 前等待清理。模拟器冷启动 `runAppReturned` 达到约 11.4 秒；目标目录最终虽被删除，但形成不可接受的启动性能回退，因此该实现未保留。

改为异步清理后重新构建、覆盖安装并注入：

- 目标目录：`mobile-image-source-interrupted-2`；
- 保留目录：`another-feature-cache`；
- 保留文件：`mobile-image-source-keep.txt`。

最终结果：

- `runAppReturned`：2,887 微秒；
- `firstFrameworkFrame`：248,507 微秒；
- 2 秒检查时目标目录仍存在，证明清理没有阻塞首帧；
- 后续检查目标目录已删除；
- 无关目录和同名前缀普通文件均保留；
- 登录态自动恢复，工作台正常显示，进程持续存活。

另增加确定性并发测试：暂停真实 `prepareStream` 编码过程，在工作目录处于活跃状态时执行启动清理；即使注入旧修改时间，该目录也不会被删除，编码完成后仍由任务自身的 `finally` 清理。

## 边界

系统缓存目录仍可能由 Android 自行回收；本修复提供确定性的应用启动补偿。iOS 使用同一 Dart 启动清理入口，但尚未在真实 iPhone 上验证目录枚举和 ImageIO 强杀场景。
