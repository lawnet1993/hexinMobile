# 移动端全业务域多端同步范围与健康上报

日期：2026-09-05

## 结论

多端同步不能只等同于聊天消息同步。移动端当前有三条独立的数据通道：

1. IM 事件通道：消息、会话、已读、@我、群资料、好友关系、成员资料与收藏等 IM 服务数据。
2. OA 事件通道：审批申请与任务、待办、通知与已读、公告、应用目录、后台表单/流程版本、考勤及日程待办等 OA 服务数据。
3. 控制面通道：登录会话、设备绑定、策略、版本更新与在线心跳。

本轮把此前只覆盖 IM 的心跳可观测性扩展为 IM 与 OA 两套独立健康状态。Windows 当前的入站故障也不能只按“聊天消息不刷新”处理：如果 Windows 统一 Gateway 未建立，依赖该通道的联系人、群资料、收藏、个人资料、OA 待办、通知和日程都必须分别验证，不能因打开页面后 REST 刷新成功就判定实时同步通过。

## 当前同步矩阵

| 业务域 | 服务端权威状态 | 移动端实时/增量机制 | 离线持久化 | 当前结论 |
| --- | --- | --- | --- | --- |
| 单聊、群聊、消息编辑/撤回 | IM | IM 长轮询事件 + ACK | SQLite + Outbox | 移动双端已通过，Windows 入站仍 P1 |
| 会话已读、未读、@我 | IM | `conversation.read` 与 mention 事件 | SQLite 单调游标 | 移动双端已通过，Windows 仍需核对 |
| 好友、群成员、群资料、个人资料、收藏 | IM | IM 事件后刷新服务端投影 | 账号隔离缓存 | 客户端链路存在，仍需逐项 Windows 多端实测 |
| 审批、待办、加签、转交、撤回 | OA | `/api/oa/sync/events` 长轮询 | SQLite + 幂等 Outbox | 两台移动设备真实流转已通过 |
| OA 通知与已读 | OA | OA 事件 + 已读待发送队列 | SQLite 单调已读投影 | 两台移动设备真实验证通过 |
| 公告、应用目录、后台表单/流程版本 | OA | OA 事件触发 bootstrap/catalog 刷新 | 账号隔离缓存 | 移动端已接入，需继续做跨端版本变更验收 |
| 考勤与日程待办 | OA | OA 事件触发 overview/bootstrap 刷新 | 账号隔离缓存 | 审批考勤回写已验证，日程需独立双端验收 |
| 会话、设备、策略、客户端版本 | 控制面 | 登录/刷新/30 秒心跳 | 安全存储，按环境隔离 | 会话与安装 ID 已接入；策略多端传播需独立验收 |

以下状态应保留为设备本地状态，不应伪装成已经跨端同步：未提交的本机审批草稿、正在编辑的消息草稿、滚动位置、下载文件、媒体缓存和临时选择器状态。若产品要求审批草稿跨端，需要服务端新增草稿版本、冲突合并和事件协议，不能只复制本地 SQLite。

## 本轮实现

- 心跳继续上报 `imSync`：传输模式、落库/ACK 游标、待 ACK 数和游标健康。
- 心跳新增 `oaSync`：传输模式、OA 已应用事件游标、待发送业务命令数、通知已读待发送数和健康状态。
- 健康读取只查询账号范围内的计数和游标，不读取或输出审批正文、通知正文、账号、设备 ID、Token 或附件地址。
- OA 本地数据库不可用时仅上报 `unavailable`，不能让健康采集阻断心跳或导致退出登录。
- 调试日志统一为 `MOBILE_COLLAB_SYNC_HEALTH`，同时呈现 IM/OA 状态且不含敏感标识。

示例结构：

```json
{
  "imSync": {
    "mode": "http_long_poll",
    "appliedSequence": 2363,
    "acknowledgedSequence": 2363,
    "pendingAckCount": 0,
    "cursorHealth": "healthy"
  },
  "oaSync": {
    "mode": "http_long_poll",
    "appliedSequence": 634,
    "pendingCommandCount": 0,
    "pendingNotificationReadCount": 0,
    "state": "healthy"
  }
}
```

## 后续多端验收必须覆盖

1. 桌面修改个人资料、好友/群设置或收藏后，移动端无需重新登录即可更新；反向同样验证。
2. 任一端新增/完成日程待办，另一端在一个事件周期内更新，离线恢复后无丢失和倒退。
3. 后台发布表单、流程或应用目录新版本，已登录桌面与移动端都切换到同一版本，不残留旧字段。
4. 一端读取 OA 通知，其他端未读立即清零；不得只改当前 UI。
5. 审批的提交、处理、加签、转交、撤回、抄送已读和考勤回写均以服务端最终状态收敛。
6. Windows 同时记录 IM 与 OA 的 transport、endpoint、connectionState、cursor、pending/ACK 和最近成功时间；打开页面后的 REST 查询只能算补偿，不能替代实时事件验收。
