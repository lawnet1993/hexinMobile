## 问题清单

### P1 / ENV-IM-001：新环境缺少可用的历史读取接口

1. 使用 test01 打开刚加入的测试群（没有本地消息缓存）。
2. 移动端按既有协议读取 `GET /api/im/conversations/{id}/messages?take=50`。
3. 重试，并以 D1 现有会话只读核对同一路径及既有单聊。

预期：200 + 消息数组。实际：两种会话均 HTTP 405、Allow: POST、空响应。请求无返回关联编号，按检查时间、方法、路径、会话 ID 定位，见 08/39。截图：[原始失败](../test/evidence/new-environment-group-20260902/04-real-load-failed.png)、[最终明确反馈](../test/evidence/new-environment-group-20260902/34-final-protocol-error.png)。

影响：首次打开、缓存缺失、向上加载历史均不能完整工作。安装中的 1.0.87 可执行文件包含同一历史读取路径，仅作为协议线索；并未操作桌面窗口复现。没有将 GET 改成 POST，后者为发送接口。另对配置内 gRPC 网关作只读探测未得到可用响应（11），不能由此断言其全部服务不可用。

处理：已向用户反馈，请后端确认路由或提供新协议。客户端保留正确读取语义，不伪造成功。

### P1 / ENV-IM-002：群消息未进入接收人的持久事件流

1. M2 在上述群用成员选择器 @test01 并发送；再发普通群消息。
2. M1 的列表摘要和未读增加，进入群无正文。
3. D1 test01 只读获取 `/api/im/sync/events?afterSequence=0&waitSeconds=0&take=500`。
4. M2 在独立单聊发送对照消息，确认同一 API 能返回其 message.created。

预期：组内消息对接收人提供可重放 message.created。实际：16:41 最终事件游标 22，三条群消息对应事件数为 0；单聊 message.created 正常。HTTP 200，无响应关联编号。完整事件编号、序号及会话 ID 见 19/39，群创建事件序号为 9。影响：群聊实时、离线补齐、@提醒定位及已读验收阻断。

处理：等待后端确认事件路由/扇出或新版协议。不将 bootstrap 的最后消息摘要当成完整消息，也不从缺失消息推导已读。

### P2 / MOB-IM-001：发送成功后，会话摘要仍等待事件回声（已修复）

原现象：M2 群内可见已确认消息，返回列表仍是建群时的空摘要和时间（16）。原因：发送确认事务只替换消息/移除 Outbox，没有同步更新 im_conversations。

修复：在同一 SQLite 事务中更新本会话加密摘要、最新序号和时间；仅接受比现有序号新的确认，不回退更晚消息，不更改其他会话/账号，不修改未读、@序号和阅读游标。实机最终验证 37/38 通过；重启加密持久化和重复/乱序确认由新增测试覆盖。

### P2 / MOB-IM-002：永久错误触发默认十次自动重试（已修复）

组件测试初次暴露加载器合计调用 12 次（默认重试加手动重试）。现为永久 4xx、取消或解析/逻辑错误不自动重试；超时、断网、408/429/5xx 最多两次短退避，仍可手动重试。聊天窗口及旧消息列表 provider 共用规则，不影响 Outbox/心跳的独立恢复策略。

405 显示明确兼容性错误；组件回归覆盖失败显示、点击重试、服务恢复后显示正文，最终加载次数为 2。
