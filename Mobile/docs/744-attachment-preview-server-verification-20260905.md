## 1. 验证原则

- 以更新后的线上接口实际响应为准，不以文档或旧桌面源码推断。

- 只使用既有 AI-UAT 附件；脚本创建的短期预览会话均在结束时撤销。
- 原件只用 `Range: bytes=0-0` 核对，未完整下载。

- OA 附件预览创建已返回结构化 200 响应。

## 5. 当前阻塞：预览内容 Range 返回 500

对视频和封面预览内容分别发送合法单段请求 `Range: bytes=0-31`，两者均返回 500：

| 目标 | 状态 | 请求编号 | 缺失 |
| --- | ---: | --- | --- |
| IM 视频预览内容 | 500 | `e823a841-fb2c-4cf8-bc87-04ae737258d1` | 无 `Content-Range` |
| IM 封面预览内容 | 500 | `d8ebf043-7bb3-4c82-9429-6f6d13441abe` | 无 `Content-Range` |

本轮还把 Range 调整为新会话的第一个内容请求，未先发送 HEAD，结果仍稳定复现 500；可以排除 HEAD 消耗或污染会话。随后同一会话的 HEAD 返回 200，且声明 `Accept-Ranges: bytes`；同一附件的登录态原件接口返回 206。因此问题集中在 `attachment-preview-sessions/{sessionId}/content` 对 Range 的处理，不是附件不存在、登录失效或整体断网。

服务端需要重点检查：

1. ticket 内容端点是否把 Range 请求传给底层对象读取逻辑。
2. `bytes=start-end` 的解析、边界截断和响应流长度是否一致。
3. 206 时是否设置合法 `Content-Range`、`Content-Length` 和 `Accept-Ranges`。
4. 超界请求是否返回 416 及 `Content-Range: bytes */总长度`。
5. 单段最大 4 MiB 的限制是否在读取前验证，不能以 500 代替协议错误。

该问题修复前，移动端不能把“分片播放、断点续传”判定为完成，也不能用不带 Range 的完整 GET 冒充边下边播。

## 6. 当前移动端差异

本轮已先修正不会依赖 Range 的部分：

- 视频封面模型补齐 `coverContentType`、`coverSize`、`coverSha256`，并与对象 ID、宽高一起经过 JSON/SQLite 路径。
- 视频发送只在封面上传结果完整有效时提交六个封面字段；封面失败不会残留部分字段。
- 接收端封面缺失或加载失败时只显示占位，不再下载原视频生成缩略图。
- 本机选取视频的封面改为约 750 ms 帧、JPEG 质量 82、最大宽度 960。
- 新增预览 Repository：校验相对 ticket URL、移动设备身份、单段最大 4 MiB、200/206/416、Content-Range 和 404/410。
- 新增预览 Manager：账号与环境隔离路径、合法 `.part` 续传、取消代次、一次会话重建、长度与 SHA-256 校验、原子发布完整文件。

尚未标记完成：

- 将预览 Manager 接入聊天播放页和应用前后台生命周期；服务端 Range 修复前接入会导致真实视频不可播放，因此暂不替换现有显式打开路径。
- 真机弱网、前后台、杀进程、账号切换的完整播放验收。
- iOS 真机验收。
- IM 普通文件附件预览需补充有效普通文件样本。
